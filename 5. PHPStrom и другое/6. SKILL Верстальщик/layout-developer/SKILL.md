# Layout Developer

Перенос дизайна из Figma в шаблон 1С-Битрикс: HTML-структура, SCSS-блоки, подключение ассетов.

Пользователь не обязан писать техзадание. Скилл задаёт минимум вопросов, дальше работает по своим справочникам.

## Привязка к проекту

Правила в `references/` написаны без путей и без имён конкретного проекта. Вместо них стоят placeholder'ы вида `<blocks-dir>`, `<hover-mixin>`, `<APP>` — это слоты, объявленные в `PROJECT.md` рядом с этим файлом. Контракт — единственный файл, который переписывается при переносе скилла в другой проект.

Перед первой правкой открыть `PROJECT.md` и подставить значения слотов. Placeholder, доехавший до кода проекта, — это баг: `<слотов>` в готовых файлах не остаётся.

Если слоты пусты (стоят `—`) — выполнить бутстрап:

1. Прочитать `CLAUDE.md` / `AGENTS.md` проекта.
2. Найти корень шаблона, папку блоков и её индекс, page-стили, хелперы, UI-примитивы, каталог расширений.
3. Выписать реальные имена: строку импорта хелперов, миксины адаптива, миксин hover, API типографики, класс контейнера и каркаса, глобальный JS-объект и диспетчер готовности.
4. Найти источник токенов и список действующих расширений.
5. Показать пользователю заполненный черновик и дождаться подтверждения.
6. Сохранить и дальше работать только по нему.

Значения по памяти не угадывать и не переносить из другого проекта. Слот пуст, а факт нужен — спросить, а не додумать. Слот, для которого в проекте нет аналога, оставить пустым и сказать об этом: правило, опирающееся на него, дальше не применяется.

## Маршрутизация

| Задача | Читать |
|---|---|
| HTML-структура, BEM, контейнеры, семантика тегов, изображения | `references/html.md` |
| SCSS: где лежит файл, вложенность, адаптив, hover, токены | `references/scss.md` |
| Перенос макета из Figma | `references/figma.md` |
| Подключение JS и CSS, `Extension::load`, кэш компонента | `references/bitrix-assets.md` |
| PHP-специфика Битрикса: страницы, инклуды, редактируемые области | `references/bitrix.md` |
| Слайдер, карусель, pagination, стрелки | `references/block-types/slider.md` |

Нужный справочник читается целиком до начала правок. Новый тип блока добавляется файлом в `references/block-types/` и строкой в эту таблицу.

## Мастер вопросов

Если пользователь не дал готовую постановку, задать первым один вопрос:

```text
Что делаем?

1. Страницу: общий скелет
2. Страницу: скелет + внутренние блоки
3. Внутренний блок в готовом скелете
```

Дальше спрашивать только недостающее: имя BEM-блока, Figma-ссылку или node, целевой файл. Что делает каждый режим — в `references/figma.md`.

Если непонятно, в какой файл писать разметку, — осмотреть проект, предложить конкретный файл и дождаться ответа. Не гадать и не создавать новый файл вместо существующего.

Если в переносимом содержимом есть изображения, до генерации HTML задать второй вопрос:

```text
Как вставляем изображения?

1. picture: адаптивные изображения под разные разрешения
2. img: одно изображение
```

Молча выбирать режим нельзя. При выборе `picture` — запросить Figma-ссылки на версии для других разрешений и не выдумывать те, которых не дали.

## Границы вёрстки

Вёрстка и натяжка на Битрикс — разные этапы, и смешивать их без просьбы нельзя.

На этапе вёрстки: HTML, SCSS, статический контент из Figma, frontend-интерактив.

На этапе вёрстки **не** делать: подключение компонентов, работу с инфоблоками, backend-логику, замену статики на динамику.

На этапе натяжки не переименовывать BEM-блоки, созданные на вёрстке, и не смешивать натяжку с новой pixel-perfect доработкой.

## Карта токенов

Если в проекте нет человекочитаемой карты дизайн-токенов, её можно сгенерировать: собрать таблицу из переменных проекта и переменных Figma и положить рядом с реализацией токенов.

Делать это **только по явной команде пользователя**. Мастер вопросов такое не предлагает и сам файл не создаёт.

## Запреты

- Не создавать `PLANNING.md`, `docs/plans` и отдельные MD-планы для страниц и блоков — процедура уже описана в `references/figma.md`.
- Не менять каркас страницы, шапку и подвал без отдельного согласования.
- Не редактировать ядро Битрикса.
- Не редактировать генерируемые артефакты сборки — только исходники.
- Не выдумывать контент, которого нет в Figma. Нет ассета — понятный placeholder с привязкой к node или вопрос пользователю.

Правки файлов выполняются по правилам согласования проекта из `CLAUDE.md` / `AGENTS.md`: сначала сказать, что именно меняется, потом дождаться подтверждения.

## Чеклист

- Нужный справочник прочитан, `PROJECT.md` заполнен.
- Режим работы выбран явно, а не угадан.
- Для изображений выбран `picture` или `img`.
- HTML прошёл чеклист `references/html.md`.
- SCSS прошёл чеклист `references/scss.md`.
- Если подключались JS или CSS — пройден чеклист `references/bitrix-assets.md`.
- Лишних файлов и MD-планов не создано.
