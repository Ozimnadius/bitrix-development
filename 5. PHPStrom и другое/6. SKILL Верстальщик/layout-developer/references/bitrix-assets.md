# Подключение JS и CSS

Единственный правильный способ подключать клиентские скрипты и стили в Битриксе: расширения ядра, точки их загрузки и три правила, нарушение которых ломает сайт молча или только на кэше.

Правила выведены из устройства ядра. Каждое из них уже было нарушено на практике и дало реальную поломку.

Имена в угловых скобках — слоты `PROJECT.md`: неймспейс расширений, глобальный объект проекта, диспетчер готовности, каталог расширений. В код они не попадают: сначала подставляется значение из контракта, и если слот пуст — сначала бутстрап.

## Где живёт клиентский код

Собственный JS и вендорные библиотеки лежат в расширениях:

```text
<ext-dir>/<имя>/
  config.php          — описание расширения
  <имя>.js            — код
  vendor/             — библиотека, скопированная из node_modules/
```

`config.php` возвращает массив:

```php
<? if (!defined("B_PROLOG_INCLUDED") || B_PROLOG_INCLUDED !== true) die();

return [
    "js"  => ["./vendor/swiper-bundle.min.js", "./swiper-group.js"],
    "css" => "./vendor/swiper-bundle.css",
    "rel" => ["<ns>.core"],
];
```

- порядок внутри `js` значим: библиотека идёт перед своим хелпером;
- `rel` — зависимости, ядро само поднимает их первыми и не дублирует;
- относительные пути считаются от каталога расширения, абсолютные остаются как есть.

Имя расширения соответствует пути: `<ns>.swiper` → `<ext-dir>/swiper/`. Ядро ищет каталог сначала в `/local/`, поэтому регистрировать модуль не нужно. Имя обязано содержать минимум два сегмента через точку.

Загрузка — всегда через `\Bitrix\Main\UI\Extension::load("<ns>.<имя>")`. Прямые `Asset::addJs()` / `Asset::addCss()` для вендорных библиотек не используются.

## Порядок регистрации в ядре

Основа всех трёх правил. При выводе компонента `CBitrixComponentTemplate::IncludeTemplate()` выполняет строго по порядку:

| Что | Когда |
|---|---|
| `result_modifier.php` | до всего остального |
| авто-подключение `style.css` шаблона | после `result_modifier` |
| авто-подключение `script.js` шаблона | после `style.css` |
| `template.php` | после `script.js` |
| `component_epilog.php` | после вывода шаблона, последним |

Запомнить: **`script.js` и `style.css` компонента регистрируются раньше, чем выполняется `template.php`, и тем более раньше эпилога.**

## Правило 1. Кэш

Вывод шаблона находится внутри `startResultCache()`. На кэш-попадании `template.php` и `result_modifier.php` **не выполняются вовсе** — ядро отдаёт готовый HTML и восстанавливает лишь ограниченный набор ассетов:

- собственные `style.css` и `script.js` шаблона;
- то, что добавлено через `$this->addExternalCss()` и `$this->addExternalJs()`.

Обычные `Asset::addCss()` и `Asset::addJs()`, вызванные из `template.php`, в этот набор **не попадают и теряются**. Компонент отрисуется из кэша, а его библиотека не подключится.

Отсюда:

- из `template.php` подключать ассеты только через `$this->addExternalCss()` / `$this->addExternalJs()`;
- расширения грузить из `component_epilog.php` — он выполняется на каждом хите, включая кэшированный;
- из `header.php` и со страниц `Extension::load()` можно звать напрямую: там кэша компонента нет.

Дефект латентный: при выключенном автокешировании всё выглядит рабочим. Проверять только с включённым кэшем и обязательно вторым проходом — первый лишь наполняет кэш.

## Правило 2. Порядок CSS

Стили компонента и библиотеки часто имеют одинаковую специфичность — тогда решает порядок подключения. `.swiper-slide { display: block }` против `.some-block__slide { display: grid }` — ровно такой случай.

Расширение грузится из эпилога, то есть **позже** и `template.php`, и авто-подключаемого `style.css`. Значит по умолчанию библиотека перебивает компонент.

Поэтому компонентный CSS, который перекрывает библиотечный, регистрируется в эпилоге сразу после `Extension::load()`:

```php
<? if (!defined("B_PROLOG_INCLUDED") || B_PROLOG_INCLUDED !== true) die();

/**
 * @global CMain $APPLICATION
 * @var string $templateFolder
 */

\Bitrix\Main\UI\Extension::load("<ns>.swiper");
$APPLICATION->SetAdditionalCSS($templateFolder . '/index.css');
```

Порядок задан явной последовательностью в одном файле и одинаков на кэш-миссе и кэш-попадании.

Если компонентный CSS ничего не перекрывает, его можно оставить в авто-подключаемом `style.css`.

## Правило 3. Условная загрузка

`script.js` шаблона подключается ядром **всегда**, когда компонент рендерится. `Extension::load()` в эпилоге при этом может стоять под условием.

Поэтому скрипт не имеет права считать, что API расширения существует — он обязан проверить своё условие сам, зеркально PHP-условию, обычно по наличию узла в DOM:

```js
window.<APP>.<onReady>(() => {
  if (!document.querySelector(".some-block__gallery")) {
    return;
  }

  window.<APP>.<initSlider>({ /* ... */ });
});
```

Без такой проверки страница, где компонент есть, а слайдера нет, падает с `... is not a function`.

Условие, вычисленное в шаблоне, передаётся в эпилог через `$templateData` — ядро кладёт его в кэш вместе с разметкой:

```php
// template.php
$templateData = ["hasSlider" => !empty($arResult["HAS_SLIDER"])];

// component_epilog.php
if (!empty($templateData["hasSlider"])) {
    \Bitrix\Main\UI\Extension::load("<ns>.swiper");
}
```

## Инициализация на стороне JS

Компонентный `script.js` не инициализирует библиотеку напрямую, а декларирует конфигурацию через хелпер внутри диспетчера готовности:

```js
(() => {
  "use strict";

  window.<APP>.<onReady>(() => {
    window.<APP>.<initSlider>({
      root: ".some-block__slider",
      swiper: ".some-block__swiper",
      pagination: ".some-block__pagination",
      prev: ".some-block__arrow--prev",
      next: ".some-block__arrow--next",
      options: {
        slidesPerView: 1,
        loop: true,
      },
    });
  });
})();
```

Почему обёртка обязательна: в момент выполнения `script.js` расширение ещё не загружено — эпилог отработает позже. В момент выполнения колбэка оно уже на месте. Сам диспетчер при этом обязан быть доступен всегда, то есть его расширение грузится глобально из `header.php` — иначе обёртка падает раньше, чем спасает.

Диспетчер выполняет функцию по `DOMContentLoaded`, а затем повторно при обновлении DOM — на событиях композита и ajax. Хелперы обязаны быть идемпотентными: повторный вызов не создаёт второй инстанс.

## Куда какой вызов

| Откуда грузим | Когда | Кэш-безопасно |
|---|---|---|
| `header.php` | нужно на всех страницах | да, кэша компонента нет |
| `index.php` страницы | нужно на конкретной странице | да, кэша компонента нет |
| `component_epilog.php` | нужно компоненту | да, выполняется на каждом хите |
| `template.php` | **не использовать** для расширений | нет, теряется на кэше |
| `result_modifier.php` | **не использовать** для ассетов | нет, теряется на кэше |

## Добавление новой библиотеки

1. Скопировать библиотеку из `node_modules/` в `vendor/` своего расширения.
2. Создать `config.php` с `js`, `css` и `rel`.
3. Написать хелпер, который вешает свой метод на глобальный объект проекта.
4. Загрузить расширение из нужной точки по таблице выше.
5. Если стили компонента перекрывают библиотечные — перенести их регистрацию в эпилог после `Extension::load()`.
6. Если загрузка условная — добавить зеркальную проверку в `script.js`.
7. Дописать расширение в таблицу `PROJECT.md`.

## Чеклист

- Вендорная библиотека лежит в `vendor/` своего расширения, а не в шаблоне.
- `Extension::load()` вызывается из `header.php`, страницы или `component_epilog.php` — но не из `template.php`.
- В `template.php` нет `Asset::addCss()` / `Asset::addJs()`; вместо них `$this->addExternalCss()` / `$this->addExternalJs()`.
- Компонентный CSS, перекрывающий библиотечный, зарегистрирован в эпилоге после `Extension::load()`.
- При условной загрузке в `script.js` есть зеркальная проверка.
- Вся инициализация обёрнута в диспетчер готовности.
- Проверено с включённым автокешированием, вторым проходом; консоль чистая и на странице с блоком, и без него.
- В итоговом коде не осталось неподставленных `<слотов>`.
