# Архитектура шаблона

Что именно разворачивается и почему так. Читать перед копированием заготовок: половина решений здесь неочевидна, и переизобретать их не нужно.

## Карта

```text
local/templates/<template>/
  header.php                каркас страницы: <head>, wrapper, открытие page-зон
  footer.php                закрытие page-зон, подвал, </body>
  inc/page_vars.php         флаги страницы, подключается первой строкой header.php
  page_blocks/
    header.php              разметка шапки сайта
    footer.php              разметка подвала
    aside.php               диспетчер боковой колонки
  styles.scss               точка входа SCSS
  css/
    core/                   переменные, шрифты, базовые стили тегов
    ui/                     примитивы: контейнер, типографика, кнопки
    blocks/                 BEM-блоки, по файлу на блок
    helpers/                миксины: брейкпоинты, hover, transition
    pages/                  стили отдельных страниц
  js/scripts.js             общесайтовые скрипты

local/js/<ns>/
  core/                     диспетчер инициализации
  base-css/                 normalize + reset
  swiper/  fancybox/        библиотеки с хелперами
```

Всё живёт в `local/`. Каталог `bitrix/` — вендорный код платформы, он перезаписывается при обновлениях и не редактируется.

## Каркас страницы

`header.php` и `footer.php` — две половины одного файла: первый открывает теги, второй закрывает. Между ними Битрикс подставляет содержимое страницы.

Первой строкой `header.php` подключает `inc/page_vars.php`. За счёт `include` вычисленные там переменные видны и в `footer.php` — иначе закрывающая половина не знала бы, какие зоны нужно закрыть.

Разметка шапки и подвала вынесена в `page_blocks/`, чтобы каркас оставался читаемым: в `header.php` видно только структуру страницы, а не содержимое шапки.

## Флаги страницы

`page_vars.php` превращает свойства страницы и её путь в набор булевых флагов. Это единственное место, где каркас принимает решения; сами страницы ничего не знают про разметку обёрток.

| Флаг | Откуда | Что делает |
|---|---|---|
| `$isMain` | путь `/` | на главной каркас `page` не строится вообще |
| `$showTitle` | свойство `show_title` | выводит `h1` заголовка раздела |
| `$showBreadcrumbs` | свойство `show_breadcrumbs` | выводит хлебные крошки |
| `$widePage` | свойство `wide_page` | страница без ограничивающего контейнера |
| `$contentLayout` | свойство `content_layout` | добавляет класс семантической типографики на `main` |
| `$showAside` | свойства раздела | включает двухколоночную сетку с боковой колонкой |

Свойства страницы ставятся вызовом `$APPLICATION->SetPageProperty()` на самой странице, свойства раздела — в `.section.php` через `$arDirProperties`. Значения по умолчанию выбраны так, чтобы обычная внутренняя страница работала без единого свойства.

Флаг «страница детальная» вычисляется сравнением пути запроса с каталогом физического обработчика: для SEF-разделов список и детальная — один и тот же `index.php`, и различить их можно только по URL.

## Боковая колонка

Колонка включается свойством раздела, а не разметкой страницы. При включённом флаге каркас строит сетку `page__grid` и подключает диспетчер `page_blocks/aside.php`, который делает две вещи: выводит файл `sect_aside.php` из каталога текущего раздела через `bitrix:main.include` и показывает отложенный слот `ShowViewContent('aside')`.

Отложенный слот нужен, чтобы шаблон компонента с детальной страницы мог дописать в колонку свой контент вызовом `AddViewContent('aside', $html)` — то есть колонка наполняется и статикой раздела, и динамикой страницы.

В DOM колонка стоит **до** контента, а визуально справа — порядок задаётся стилями. Так на мобильном она оказывается под контентом без дублирования разметки.

Чтобы свойства колонки можно было ставить из админки, их нужно один раз зарегистрировать в списке типов свойств модуля управления структурой. Регистрация хранится в базе, а не в файлах, поэтому на новой копии сайта её придётся повторить. Без регистрации свойства всё равно работают — но проставлять их придётся руками в `.section.php`.

## Слои SCSS

Порядок подключения в `styles.scss` значим — он определяет, кто кого перебивает при равной специфичности:

1. `core/variables` — токены; должны быть объявлены раньше всех, кто их использует;
2. `core/fonts` — `@font-face`;
3. `core/adjustment` — базовые стили тегов и каркаса;
4. `core/globals` — общие правила проекта;
5. `ui` — примитивы: контейнер, типографика, кнопки;
6. `blocks` — BEM-блоки.

Блоки идут последними, чтобы блок мог перекрыть примитив, а не наоборот.

`helpers` в точку входа не подключается: там только миксины и переменные Sass, они не дают CSS-вывода и импортируются в каждый файл отдельно строкой `@use "../helpers/index" as *`.

`pages/` в точку входа тоже не подключается: стили отдельной страницы компилируются в свой CSS и подключаются на самой странице, чтобы не грузить их на всём сайте.

## Токены и темы

Два слоя переменных. Raw-слой повторяет имена из макета один в один — по нему сверяются с дизайнером. Семантический слой (`--bg`, `--text`, `--accent`, `--border`, `--font-heading`) ссылается на raw и используется в блоках.

Смысл разделения виден на второй теме: тема переопределяет только семантический слой, raw-палитра остаётся общей. Блок, написанный на семантических токенах, переключается сам; блок с raw-значениями ломается.

Тема ставится атрибутом на `<body>` в `header.php` по разделу сайта. Если тема одна, этот код не создаётся, но семантический слой всё равно нужен: он и есть договор между дизайном и вёрсткой.

Рядом с реализацией лежит `css/design-system.md` — человекочитаемая карта того же самого: raw-имена из макета, семантические токены по темам, шрифты и типографика. Она нужна не как документация ради документации: без неё вёрстка каждый раз читает `_variables.scss` и всё равно не знает, какому имени в макете соответствует переменная. Скаффолдер создаёт её пустой, значения приходят из макета.

## Хелперы

Брейкпоинты объявлены переменными и обёрнуты миксинами `xs`/`sm`/`md`/`lg`/`xlg` — прямые `@media` в блоках запрещены, иначе набор точек расползается по проекту.

Миксин `hover` вместо `:hover` — он разделяет устройства с курсором и без: на тач-устройстве вместо hover срабатывает `:active`, иначе состояние залипает после тапа.

## Расширения и диспетчер

Клиентский код подключается расширениями ядра, а не прямыми `Asset::addJs()`. Расширение — это каталог с `config.php`, где перечислены `js`, `css` и зависимости `rel`; ядро само поднимает зависимости в правильном порядке и не дублирует их.

Расширение `<ns>.core` даёт диспетчер `<APP>.onReady(fn)`. Он не эквивалент `DOMContentLoaded`: помимо первой загрузки он переигрывает все зарегистрированные инициализаторы при обновлении DOM — на событиях композитного кэша и ajax. Без этого блоки, приехавшие ajax'ом, остаются мёртвыми.

Диспетчер грузится глобально из `header.php` и обязан быть доступен всегда: скрипты шаблонов компонентов выполняются раньше, чем их расширения, и оборачивают себя в `onReady` именно поэтому.

Хелперы библиотек (`initSwiperGroup` и подобные) обязаны быть идемпотентными и убирать инстансы при подмене DOM — иначе повторный прогон диспетчера создаст второй слайдер поверх первого.

Полные правила подключения ассетов, включая три кэш-правила Битрикса, — в скилле `layout-developer`, файл `references/bitrix-assets.md`.
